# Shared Minter contract

One platform Minter supports multiple DAO Tokens. It is deployed separately from the six DAO modules and has per-token allocations, not a global stored administrator.

## Interface

```text
mint_batch(token_id: Address, recipients: Vec<Address>, amounts: Vec<u128>)
set_merkle_root(token_id: Address, root: BytesN<32>)
mint_merkle(token_id: Address, recipient: Address, amount: u128, proof: Vec<BytesN<32>>)
set_allowlist(token_id: Address, addresses: Vec<Address>, fixed_amount: u128)
mint_allowlist(token_id: Address, recipient: Address, amount: u128)
```

Here `token_id` means the **Token contract address**, not an NFT number. Every operation requires a Live token. The token's admin (`token.admin()`, the Treasury after launch) authorizes batch and configuration operations, so they require governance. Claims require recipient auth and Minter mint authority on the Token.

`mint_batch` accepts 1–18 recipient entries (`common::MAX_BATCH_RECIPIENTS`, `BatchTooLarge`); the Token also requires the whole batch to fit its event budget (`common::batch_mint_fits`: up to 43 tokens to one recipient, fewer across several). Errors raised by the Token (for example its `BatchTooLarge` 7205 or a missing mint authority) propagate unchanged. Merkle proofs have at most 32 siblings. The leaf is `sha256(recipient_xdr || amount_be_u128)`; each internal node hashes its sorted pair. Merkle and allowlist claims have separate rounds; replacing one allocation starts that method's round. Allowlist amounts must equal the configured amount, so a claim larger than 43 tokens cannot be minted in one call.

Every entry point extends the Minter's own instance TTL, so the shared contract stays live while used; per-token entries follow the long-lived persistent policy.

Before launch founders mint directly through the Token; the Minter is not a setup tool. The Manager registers the platform address and launch can grant it authority using the pinned `expected_minter`. Only DAO governance can revoke that grant.
